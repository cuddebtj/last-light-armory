# Contributing

Thanks for looking at last-light-armory. This repo holds two genuinely
different things — a Next.js site (`web/`) and a Go scoring job
(`scoring/`) — see the root [`README.md`](README.md) for how they relate,
and each subproject's own README for its specific setup.

## Before you start

1. Pick the right subproject. If your change is only about how weapons are
   displayed, filtered, or sorted, you're in `web/`. If it's about how
   scores are computed, you're in `scoring/`. Most changes touch exactly
   one; CI is scoped the same way (`.github/workflows/web-ci.yml` and
   `scoring-ci.yml` each gate only on their own `paths:` filter), so a
   pure-`web/` PR never waits on `scoring/`'s CI and vice versa.
2. Read that subproject's README for setup. `web/` needs nothing but
   `npm install`. `scoring/` needs a Postgres connection string — if you
   don't have one, you can still read/modify the pure logic in
   `internal/scoring/` and run its unit tests, but you won't be able to
   run `cmd/score` itself or the integration suite.
3. If your change needs a fact Bungie's manifest carries that isn't
   currently in the database (a new weapon field, a new stat), that
   belongs in the sibling [`last-light-armory-ingest`][ingest] repo, not
   here — see its own CONTRIBUTING.md.

## Branching and commits

- Never commit directly to `main` or `dev`. Branch off `dev`, open a PR
  back into `dev`.
- Branch names are `type/short-description` — `feature/...`, `fix/...`,
  `chore/...`, `docs/...`. Look at recent branches (`git branch -a`) for
  examples.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org/):
  `type(scope): summary`, e.g. `feat(web): add champion-mod filter`,
  `fix(scoring): renormalize weights when a column is missing`. Scope is
  usually `web`, `scoring`, `scripts`, or `data` for a data-only refresh.
  The summary describes *why*, not a restatement of the diff.
- Keep PRs scoped to one logical change. A bug fix doesn't need a drive-by
  refactor bundled in; a new feature's tests belong in the same PR as the
  feature, not a follow-up.

## What a PR needs to pass

Both subprojects enforce their bar in CI, not by convention — a PR that
doesn't pass these won't merge:

**`web/`**
```sh
npm run build             # must succeed, including the TypeScript check
npm run lint               # ESLint clean
npm run test:coverage      # fails under 98% statements/branches/functions/lines
npm run test:e2e           # Playwright, against the real production build
```

**`scoring/`**
```sh
go build ./...
go vet ./...
gofmt -l .                 # must produce no output
go test -tags integration -coverprofile=cover.out ./internal/...   # fails under 98%
```
(`scoring-ci.yml`'s `test` job runs this against a real Postgres service
container — see that workflow file if you need to reproduce it locally
without your own database.)

New code lands with its own tests in the same PR — that's how the 98%
floor stays real instead of eroding one exception at a time.

## Verifying a change actually works

Passing tests isn't the same as verifying the feature works. Before
opening a PR:

- **`web/` UI changes**: run `npm run dev` and actually use the feature in
  a browser — check the golden path and at least one edge case. Type
  checks and test suites verify code correctness, not feature correctness.
- **`scoring/` changes that touch the formula or a database write**: run
  the relevant command for real against a database you have access to and
  spot-check the result by hand (row counts, bounds, a hand-computed
  example) before trusting it — see the git history for `cmd/score` and
  `cmd/import-baseline` for the pattern this project follows: capture
  before-state, run for real, verify bounds/spot-check by hand, rerun and
  confirm identical output (idempotency), only then commit.

## Data and secrets

- `scoring/.env` (copied from `.env.example`) holds a real database
  connection string — never commit it, never paste it into a commit
  message or PR description.
- `web/data/*.json` **is** committed — it's the static snapshot the site
  builds from. Don't hand-edit it; it's regenerated by
  [`scripts/publish.sh`](scripts/publish.sh), which also runs the full
  `web/` test suite against the refreshed data before it's allowed to
  commit.

## Code style

- **Go**: idiomatic, `gofmt`-clean, `go vet`-clean, `staticcheck`-clean.
  Table-driven tests for anything with real branching. Doc comments on
  every exported identifier — `go doc ./...` should read like a spec, not
  require guessing from the name.
- **TypeScript**: ESLint-clean. Comments explain *why*, not *what* — a
  non-obvious constraint, a workaround, a design trade-off. Skip comments
  that just restate what well-named code already says.

Both languages: no dead code, no speculative abstractions for a single
call site, no error handling for scenarios that structurally can't happen.
If you're unsure whether something needs a comment, ask: would removing it
confuse the next person reading this? If not, leave it out.
